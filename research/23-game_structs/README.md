# Game structs across builds

Every game struct and class in nocedit.exe, nocturne.exe (retail), bw1.exe, blairwitch2.exe and
bw3.exe: its size, its fields, and where each field sits in each build.

| File | Contents |
|------|----------|
| `index.md` | Every game struct: its size and state in each build; ✓ where the layout is the size the build's own RTTI records |
| `changes.md` | Per build, against nocedit: the structs whose size changed, how many fields moved, how many are not placed |
| `structs/<Name>.md` | One struct: sizes per build, every field's offset in each build, the undefined bytes each layout leaves |
| `structs.json` | All of it, machine-readable |
| `known_layout_changes.json` | Hand-read layout changes: per build and struct, its shifts, the fields the build added, its size where no RTTI gives it, and the basis |
| `bw_own_structs.json` | Layouts of the BW games' own types (the field notes), read from their code, with the method and vtable names; applied by `define_structs.py` |

All but `known_layout_changes.json` are generated by `scripts/Python/struct_layout_report.py`
from the exported data types; regenerate rather than edit. `known_layout_changes.json` is kept by
hand, and only changes the code settles go in; `plan_struct_transfer.py --known` reads it. Vtable
structs are with the actor hierarchy (`22-actor_class_hierarchy/`).

## Where the Blair Witch layouts come from

The BW programs' structs started as placeholders: sized by Watcom RTTI where the build has a
record, empty otherwise. nocedit's layouts were copied onto them in two passes, both planned by
`plan_struct_transfer.py` and applied by `import_sibling_types.py --replace-stubs`.

The evidence is matched code. `export_typed_accesses.py` records, for every load and store in
nocedit's matched functions, the struct nocedit's decompiler types the access with and the offset
it addresses. `derive_struct_drift.py --typed-accesses` then pairs each such instruction with the BW
one: `[reg + X]` in nocedit against `[reg + Y]` in BW is a sighting that the struct's offset X is Y
in BW. A sighting counts only when X is the recorded offset and lies inside the struct's nocedit
size, so it cannot be credited to the wrong object. This sees value types and records that no
method of their own touches (`C3DSCamera`, filled by the `.3ds` loader). A sighting inside a
member held by value is passed down to that member too, at the member's own inner offset, with
the member's BW start taken from the container's shift: a `CDrummer` sighting in
`base.base.carry_hands[1]` is a sighting of `SCarryHand`.

Instruction streams of equal length are paired by position. Pairs whose length changed are
paired by difflib over instruction shapes (`--align`). Those sightings never called a shifted
struct unchanged, but runs of like stores can pair one slot off and show a false shift
(`CBox`, `CMirror`, `CWeather`). So they only settle a struct the equal-length code does not
observe, and only as unchanged; a shift they show alone is checked by reading the code
(`CTrigger` and `CElephantGun` were real, below).

Sizes come four ways, each scored against RTTI where a record exists, with none wrong:

- **Allocations** (`find_allocation_sizes.py`). Watcom compiles `new CFoo` as a call to operator
  new with the size as the last push, then hands the result to the constructor as a pushed
  `this` (cdecl): `push 0x34c; call operator_new; ...; push eax; call CAmmoBox_ctor`. nocedit's
  memory-debug `new` pushes a line and a file first, so the size is still the last push; the BW
  builds pass the size alone. The class is the constructor's (its name, else the last
  `g_<Class>VTable` it stores); a vtable stored right after a base constructor names a class
  with none of its own (`new CMinecar` calls CPlatform's); a singleton names its type by its
  global; an allocation still unclassed takes the class of nocedit's allocation at the same place
  in the matched function. This reads the build's own code, matched or not. Against nocedit's
  layouts it gave 121 classes right and none wrong; against BW RTTI 128 / 141 / 117. One `new`
  settles a size.
- **Spelled in the code.** Where nocedit spells a struct's size as a constant (an allocation whose
  result is typed as that struct, or an array stride of it), the paired BW instruction holds the BW
  size. Two agreeing sightings set a size; one contrary sighting is enough to refuse a verbatim copy.
- **Array elements.** A sighting in element k > 0 of a member array gives k × the element's BW size.
- **Containers.** A container's shift before and after a member implies the member's size. One
  container cannot tell a member that grew from a field added right after it, so two agreeing
  containers are needed (`CParticle` from its 7 derived classes).

- **Same size, same code.** A struct is copied verbatim when its sightings put every well-supported
  segment (3 or more) at delta 0, its RTTI or measured size equals nocedit's or it has neither,
  and everything it embeds is copied too. A matching total size alone is not enough, because a
  reordering keeps the total (`CDemonCamera` in retail; `CDemonActor` in bw1 and bw3, below). A
  struct with no size of its own is also refused when a struct embedding it shows a different
  shift before and after it: it grew at its end, which its own offsets cannot show.
- **Resized.** A field keeps its place only where the measured shift settles it: inside an observed
  segment, or between two segments that moved alike, it moves with them. Between segments that
  differ, the insertion could be on either side, so the field is not placed. After the last
  segment it is placed only when the class's whole size change equals that segment's shift.
  Offset 0, a derived class's base, never moves; a class no code observes places only that. A
  field is also not placed when its type has no known size in the build (a struct still a
  placeholder there), or when it would overlap the field before it or run past the end. The size
  is the RTTI size, else the measured one.
- **Known.** A struct in `known_layout_changes.json` is placed from its hand-read shifts, with the
  fields the build added inserted at their offsets. A hand-read shift is taken as written, offset 0
  included, and its fields may land out of order (a re-ordering, as in bw3's `CGunFlame`); a field
  is left out only where it would overlap one already placed.
- **Rebuilt.** A struct whose array lengths or field set changed, beyond what shifts can describe,
  is defined whole from `bw_rebuilt_structs.json` (as BW's own types are from `bw_own_structs.json`).

Laying out a member type also fixes the fields that hold it: Ghidra grows each into the undefined
bytes after it.

Fields not placed are left as undefined bytes, listed on each struct's page. They are either members
the build added or ones whose new offset is not yet known.

## CONFIRMED

- **Every BW layout with an RTTI record is exactly the recorded size.** That covers 196 / 194 / 145
  classes in bw1 / bw2 / bw3.
- **bw2's enemies read `CEnemy.victim` at `+0x10a78`,** which is where the resized layout places
  it. The measurement was independent: the offset came from bw2's own code in CBasicEnemy's
  `checkVictim`.
- **BW grew the character classes.** CCharacter grew 940 bytes in bw1, 19,516 in bw2 and 4,008 in
  bw3; bw2 also grew CDemonActor by 348 (`model` moves from `0x158` to `0x2b4`). `changes.md`
  lists every resized struct.
- **CDemonActor in bw1 and bw3 is nocedit's size but not its layout.** BW added one dword at
  `0x11c`, between `blood_effect_color` and `footstep_sound_code`, and dropped `is_editor_hidden`
  as retail did, so the fields from `footstep_sound_code` to `render_needs_update` sit 4 higher
  and `next_actor` is back at `0x14c`. The new field (`footstep_particle_count`): `setup` zeroes
  it; `handleFootstep` sets it to 1 for a `CShadow`, else `getRandomInt(1, 3)`, and calls the
  `core_fire.cpp` spawner that many times. The ctor, `handleFootstep` and three `CDemonSet`
  functions agree on every offset (`known_layout_changes.json`).
- **CTrigger in bw1 and bw3 added 4 bytes after `0x2f8`** (RTTI 884, nocedit 880): the ctor,
  `acceptsDamageFrom` and `applyDamage` put `triggering_actor` through `damage_cooldown` 4 higher.
- **CElephantGun in bw3 is 1440 bytes (nocedit 1412):** its own fields from `0x578` sit `0x1c`
  higher, its CWeapon base having grown by 28.
- **CSfxSlot is 284 bytes in every BW build (nocedit 296).** Its embedded `CSfxOptions` is 96
  bytes (RTTI; nocedit 112), and every field after it sits `0x10` lower.
- **SCarryHand is 120 bytes in every BW build (nocedit 68).** In bw1 and bw2 the element stride of
  CCharacter's `carry_hands[2]` measures it (7 sightings each). In bw3 CCharacter's shift is
  `+0xfc` before the array and `+0x164` after, 2 × 52 more. `bone_index`, `secondary_bone_index`
  and `carry_actor` did not move.
- **CParticle is 64 bytes in every BW build (nocedit 56),** agreed by its 7 derived classes, all
  8 bytes bigger by RTTI. **CHero is 130,988 bytes in bw1 and 153,152 in bw2 (nocedit 130,004),**
  agreed by its 7 derived classes; bw3's disagree, so it has no size there yet.
- **Measured sizes that differ from nocedit:** SSoftwareEdge 80 (nocedit 72); CSfxSample 432 in
  bw1 and bw3, 428 in bw2 (nocedit 384).
- **By allocation, in every BW build:** CBitFont 16,928 (nocedit 12,696), CTextureCache 98,316
  (nocedit 81,932; the `g_TextureCacheInstance` singleton) and CCloth 240,432 (nocedit 261,744).
  CPodFile is 1068 as in nocedit; CBodyPart, CFlies and CDemonLight, built inline, are allocated
  at the sizes their layouts already have.
- **The BW games' operator new takes the size alone.** The function the BW programs name
  `crt_unknown.c_debugAllocTracked1` is the retail `operator new`, not nocedit's
  memory-debug allocator (`push size; call`, against nocedit's `push line; push file; push size`).
- **The field notes (`core_fldnotes.cpp`) are BW's own types, laid out from their code**
  (`bw_own_structs.json`). `SPageResource` (24 bytes: x, y, width, height, link, vtable at `+0x14`)
  is the base of `SPageResourceText` (288), `SPageResourceBitmap` (44), `SPageResourceMap` (28)
  and `SPageResourceTwanaEntry` (280; 276 in bw2, which has no `slot_x`);
  `SPageResourceTwanaCharacter` (76) derives from the Bitmap. `STextView` (584) lays text and
  resources out on `STextPage`s (324: up to 80 resources); `SNotesSection` (740) holds
  `SNotesEntry`s (348); `SNotesMap` (2416; 4716 in bw3, which allows 10 sets and 15 annotations
  instead of 4 and 8) holds `SNotesMapSet`s and `SNotesMapAnnotation`s. Every size matches its new
  or its RTTI record.
- **The BW allocators:** retail `operator new` (the size alone), `operator new[]`, `malloc` and
  `calloc` are named in every BW program (`crt_memory.c_*`).
- **Arrays settle their elements.** A container whose shift is the same before and after an
  array of two or more kept the element's size: `SLod[5]` (CDeformableModel),
  `CKeyFramedModelPart[30]` (CKeyFramedModel), `SWayPointAdjacency[60]` (CWayPoint; not bw2), and
  SClothBone, SRoom, SBodyPartFire, SFly and SPart.
- **CInventory is 1,132 bytes in bw1 and 1,136 in bw3** (nocedit 1,120): CHero's ctor bounds it
  from above (its owner pointer and the next field), CInventory's own ctor from below. **bw2's
  CHero holds three inventories of 1,572** (`inventories` at `+0x2437c`): its items are split into
  5 groups, each with its own selected item and weapon (`current_group`, `item_groups[100]`,
  `selected_items[5]`, `selected_weapons[5]`), and it adds `show_compass` at `+0x8`.
- **CHero is 134,092 bytes in bw3:** its ctor's last store is `ai_task`, nocedit's last field, at
  `+0x20bc8`, and CStranger's own fields start at `+0x20bcc`.
- **bw2's enemies and NPCs share a BW base, CBasicEnemy (71,760 bytes, parent CEnemy).** Its ctor,
  the first call of every derived ctor, stores up to `+0x1184c`; CBasicNPC, derived from it, is
  71,760 by RTTI.
- **The BW-only actor classes have their base.** A class's parent comes from its
  `registerActorClass` call, else from its ctor's first call (the base ctor, `this` pushed); the
  two agree on every class both give. 30 of bw3's own classes and 8 of bw2's add no fields to
  their parent; the rest keep their own bytes undefined until read.
- **CDemonMission is 29,216 bytes in bw1 and bw3 and 17,212 in bw2 (nocedit 10,192).** Each build's
  static instance (`0x1d2c900` bw1, `0x1d182f0` bw2, `0x1d81080` bw3) ends where the actor lookup
  table does, at the next global (bw2's 4 bytes before it). BW holds 16 set names instead of 4,
  moved ahead of the flags (`num_sets` at `+0x4`, the names at `+0x8`); dropped nocedit's editor
  fields at `+0x10..+0x43`; grew the lookup table from 2,000 actors to 6,000 (3,000 in bw2); and
  turned `actors_prepared` into `prepared_set_index`, which `loadSet` compares with the current set.
  bw1 and bw3 add `teleport_requested` (`setTeleportTarget` sets it, `process` clears it); bw3 also
  moves the delete queue ahead of `mission_name`.
- **CMoon is the title screen's, 2,768 bytes in bw1 and bw2 and 2,792 in bw3 (nocedit 22,240).**
  It holds three CKeyFramedModels from `+0x8`; bw1 loads `titletwana/b/c.kfm` into them, bw2 loads
  only its title bitmaps, and bw3 adds six ints at `+0xad0` for the main menu's scrolling tiles and
  the pulsing hand.
- **bw3 re-laid out three effects.** `CBulletHole` (64) adds `decal_type` at `+0x3c`, which picks
  the texture and the size; `CFootstep` (68) adds the current hero's `area_id` at `+0x8`, moving the
  corners, `alpha` and `is_bloody` up 4; `CGunFlame` (44) puts `position` first and `lifetime` at
  `+0xc`, and adds `flame_style` and `frame_count`. A style-0 flame with a `flame_type` burns the
  characters and flame cans near it (`burnNearby`), new in bw3.
- **SBodyPartFire is 1,036 bytes in bw2** with nocedit's layout: its CFlame member is 1,024 there.
  CBodyPart's shift grows by 2 × 348 across `fires[2]`.
- **BW's own helper classes are laid out from their code** (`bw_own_structs.json`), each at its
  RTTI size: the stream classes (`CInStreamFile` 44, 40 in bw2 without `binary_mode`;
  `CInStreamMemory`, `CInStreamPipe`, `COutStreamDebug/File/Memory`), the `CCodec` ciphers
  (`CAsciiArmor`, `CAsciiUnarmor`, `CCheesyCipher`), the `CParticle` effects `CLeaf` and `CFirefly`,
  `CFieldNotes` (the notes file name and whether they are shown), `SDynamicLight`, `SIpAddr`,
  `SSocket` (nocedit's `CSocket` layout), `SButtonStruct` and the puzzles: `CChemPuzzle`,
  `CAudioRecPuzzle` (bw3 drops bw1's sound-handle block; bw2's is a different radio with 30
  buttons), and bw2's `CExamplePuzzle`, `CGameHook`, `CMuzzleEffect` (nocedit `CMuzzleFlash`'s
  layout), `SFollowSlotStruct` and `CSimpleParticleSystem`, bw1's `SDjienBox` and bw3's `CRing`.
  `CMini3D` is empty. Their bases with no type (the stream and puzzle interfaces, a vtable only)
  are a `vtable` field at `+0`. Bytes no code touches are left undefined.
- **Every class method in the BW programs takes `this_ptr` of its class.** Methods with no
  parameters get the prototype the decompiler infers when its first parameter is the first stack
  argument, where Watcom passes `this`, or `this` alone when the body reads nothing and a slot of
  the class's labelled vtable holds it (`fix_this_ptr.py`).
- **Unchanged in every BW build, by allocation size:** CVector3f, CVector3i, CQuaternion4f, CRect,
  SRenderVertex, SBone, SLayerAction, the MRGL model records and 25 more.
- **The network code is in every build, unused.** `core_netgame.cpp` (`CNetGame`) and
  `support_trisock.cpp` are compiled into nocedit, retail and all three BW games, with RTTI for
  `CNetGame` and `SNetPlayer`, and dummied out as in Nocturne. Their packet, address and input
  structs are original types, not the recreation's.
- **The applied layouts agree with the code.** Of the typed sightings on laid-out structs,
  11,511 / 11,454 / 8,882 agree with the layout in bw1 / bw2 / bw3. The 2 / 6 / 2 that do not are
  single sightings through a variable nocedit types as the wrong object.

## Unverified

- **Enum values.** `EAmmoType`, `EDamageType`, `EHeroControlType`, `EAimMode`, `EGasMaskState` and
  `EHeroTask` were imported into the BW programs from nocedit so the structs holding them could
  be laid out. Their names and values are nocedit's. BW may have added members (bw3 has new ammo
  classes).

## Not yet placed

Structs no matched code addresses stay placeholders. The drift sees an access only where nocedit
and the build's function have the same number of instructions, and only as a numbered
displacement: a struct reached only through a global (`CKeys`), only at offset 0, or only in
functions BW changed (`SFreaky`) has no sightings, and editor-only types (`CActorProperty`) have no
BW code at all. bw3's CStranger, CMobster, CSuccubus and CTentacle are not yet read. BW's own classes keep the bytes past their
base undefined until read from the code. A field whose type is still a placeholder in the build
has the placeholder's length: `ios`, and the network code's `SNetPacketHeader`, `SPlayerInput` and
`SSimFrame`.

## Regenerating

The evidence, then a plan per build (the plan is a dry run until imported):

```sh
python3 scripts/Python/find_allocation_sizes.py --program nocedit.exe --out alloc_nocedit.json
python3 scripts/Python/find_allocation_sizes.py --program bw1.exe --out alloc_bw1.json \
    --reference alloc_nocedit.json --mapping annotations/bw1.exe/reports/sibling_mapping_from_nocedit.json
python3 scripts/Python/export_typed_accesses.py --project /abs/projects --out typed.json \
    --mapping annotations/bw1.exe/reports/sibling_mapping_from_nocedit.json --mapping ...
python3 scripts/Python/derive_struct_drift.py annotations/bw1.exe/reports/sibling_mapping_from_nocedit.json \
    --include-unshifted --typed-accesses typed.json --out bw1_drift.json
python3 scripts/Python/derive_struct_drift.py annotations/bw1.exe/reports/sibling_mapping_from_nocedit.json \
    --include-unshifted --typed-accesses typed.json --align --out bw1_drift_aligned.json
python3 scripts/Python/plan_struct_transfer.py --program bw1.exe --drift bw1_drift.json \
    --drift-aligned bw1_drift_aligned.json --known research/23-game_structs/known_layout_changes.json \
    --alloc-sizes alloc_bw1.json \
    --out bw1_copy.txt --out-shifts bw1_shifts.json
```

Laying out a struct can let its containers and derived classes be planned, so plan again after
importing until the plan is empty.

The structs read whole from the code, and the receivers of class methods:

```sh
python3 scripts/Python/define_structs.py research/23-game_structs/bw_own_structs.json --program bw1.exe
python3 scripts/Python/define_structs.py research/23-game_structs/bw_rebuilt_structs.json --program bw1.exe
python3 scripts/Python/fix_this_ptr.py /abs/projects NocturneEdit bw1.exe blairwitch2.exe bw3.exe
```

Each is a dry run until `--apply` (`define_structs.py` also takes `--project`).

The pages:

```sh
python3 scripts/Python/struct_layout_report.py --out-dir research/23-game_structs \
    --program nocedit.exe --program nocturne.exe --program bw1.exe --program blairwitch2.exe --program bw3.exe
```
