# Game structs across builds

Every game struct and class in nocedit.exe, nocturne.exe (retail), bw1.exe, blairwitch2.exe and
bw3.exe: its size, its fields, and where each field sits in each build.

| File | Contents |
|------|----------|
| `index.md` | Every game struct: its size and state in each build; ✓ where the layout is the size the build's own RTTI records |
| `changes.md` | Per build, against nocedit: the structs whose size changed, how many fields moved, how many are not placed |
| `structs/<Name>.md` | One struct: sizes per build, every field's offset in each build, the undefined bytes each layout leaves |
| `structs.json` | All of it, machine-readable |

Generated by `scripts/Python/struct_layout_report.py` from the exported data types; regenerate
rather than edit. Vtable structs are with the actor hierarchy (`22-actor_class_hierarchy/`).

## Where the Blair Witch layouts come from

The BW programs' structs started as placeholders: sized by Watcom RTTI where the build has a
record, empty otherwise. nocedit's layouts were copied onto them in two passes, both planned by
`plan_struct_transfer.py` and applied by `import_sibling_types.py --replace-stubs`:

- **Same size, same code.** A class is copied verbatim when matched methods address it at the same
  offsets in both builds (every segment from `derive_struct_drift.py` with at least 3 observations
  at delta 0), its RTTI size equals nocedit's or it has none, and everything it embeds is copied too.
  A matching total size alone is not enough, because a reordering keeps the total
  (`CDemonCamera` in retail).
- **Resized.** A field keeps its place only where the measured shift settles it: inside an observed
  segment, or between two segments that moved alike, it moves with them. Between segments that
  differ, the insertion could be on either side, so the field is not placed. After the last
  segment it is placed only when the class's whole size change equals that segment's shift.
  Offset 0, a derived class's base, never moves. A field is also not placed when its type has
  no known size in the build, or when it would overlap the field before it or run past the end.

Fields not placed are left as undefined bytes, listed on each struct's page. They are either members
the build added or ones whose new offset is not yet known.

## CONFIRMED

- **Every BW layout with an RTTI record is exactly the recorded size.** That covers 173 / 166 / 124
  classes in bw1 / bw2 / bw3.
- **bw2's enemies read `CEnemy.victim` at `+0x10a78`,** which is where the resized layout places
  it. The measurement was independent: the offset came from bw2's own code in CBasicEnemy's
  `checkVictim`.
- **BW grew the character classes.** CCharacter grew 940 bytes in bw1, 19,516 in bw2 and 4,008 in
  bw3; bw2 also grew CDemonActor by 348 (`model` moves from `0x158` to `0x2b4`). `changes.md`
  lists every resized struct.

## Not yet placed

Structs with no RTTI record and no observing code stay empty placeholders, and so do classes whose
code shows shifted offsets but whose size could not be matched. Placing more fields needs more
matched methods (better function mapping) or reading the BW code around a gap.

## Regenerating

```sh
python3 scripts/Python/struct_layout_report.py --out-dir research/23-game_structs \
    --program nocedit.exe --program nocturne.exe --program bw1.exe --program blairwitch2.exe --program bw3.exe
```
