## Stable Override Types

These override types use a simple ESP anchoring strategy that is semantically safe
and should remain valid across Ghidra versions.

| Type | CLI Flag | Fix Strategy |
|------|----------|--------------|
| `callind_anchor` | `--type=callind-anchor` | `ESP = EBP - frame_offset` |
| `variadic_anchor` | `--type=variadic-anchor` | `ESP = EBP - frame_offset` |
| `stack_align_anchor` | `--type=stack-align` | `ESP = EBP - frame_offset` |
| `call_esp_anchor` | `--type=call-anchor` | `ESP = EBP - frame_offset` |

**Why These Are Stable:**

1. **Standard P-code format**: The generated P-code uses standard operations:
   ```
   INT_ADD (register,0x10,4) = (register,0x14,4), (const,0xffffffdc,4)
   ```

2. **Architectural constants**: Register offsets are x86 architectural constants:
   - `ESP = 0x10`
   - `EBP = 0x14`
   - These will not change for x86-32 in Ghidra

3. **Safe semantics**: The anchor strategy simply asserts "ESP is at a known offset
   from EBP" - this is always true in EBP-frame functions and helps the decompiler
   recover from lost ESP tracking

4. **No external dependencies**: These overrides don't rely on RAM space IDs or
   complex P-code sequences

**Generated P-code Example:**
```python
# For frame_offset = 0x24:
# ESP = EBP + (-0x24) = EBP - 0x24
"INT_ADD (register,0x10,4) = (register,0x14,4), (const,0xffffffdc,4)"
```

## Experimental Override Types

These override types use more complex save/restore patterns and have potential risks.

| Type | CLI Flag | Fix Strategy | Risk Level |
|------|----------|--------------|------------|
| `callind_preserve` | `--type=callind-preserve` | Save/restore ESP across CALLIND | High |
| `variadic_preserve_ebp` | `--type=variadic-ebp-preserve` | Save/restore ESP across CALL | Medium |
| `variadic_preserve` | `--type=variadic-preserve` | Save/restore ESP across CALL | High |
| `call_esp_preserve` | `--type=call-preserve` | Save/restore ESP across CALL | High |

**Why These Are Experimental:**

1. **Complex P-code sequences**: These generate 5-7 P-code operations:
   ```
   COPY (unique,0x10000,4) = (register,0x10,4)           # save ESP
   INT_SUB (register,0x10,4) = (register,0x10,4), (const,0x4,4)  # ESP -= 4
   STORE (const,0x1a1,4), (register,0x10,4), (const,0x...,4)     # push return addr
   CALL/CALLIND ...                                      # the call
   COPY (register,0x10,4) = (unique,0x10000,4)           # restore ESP
   ```

2. **Hardcoded RAM space ID**: The `RAM_SPACE_ID = 0x1a1` is hardcoded for x86.
   While unlikely to change, this is a potential fragility point.

3. **Semantic assumptions**: The save/restore pattern assumes:
   - The callee doesn't have observable side effects on ESP beyond its convention
   - Argument detection doesn't depend on seeing the actual ESP modifications

4. **May break decompilation**: In some cases, the decompiler may produce worse
   output because it can't see the actual stack operations

## Potential Validity Concerns

### RAM_SPACE_ID (Experimental types only)

Location: `generate_pcode_overrides.py` lines 102, 149

```python
RAM_SPACE_ID = 0x1a1
```

This value is specific to x86 in the current Ghidra implementation. If Ghidra's
address space implementation changes, experimental overrides using STORE operations
would need updating. The stable anchor types do not use this value.

### Two's Complement Conversion

The `to_twos_complement()` function correctly handles negative offsets for 32-bit:

```python
def to_twos_complement(value, bits=32):
    if value >= 0:
        return value
    return (1 << bits) + value
```

This is standard and will remain valid.

### Unique Space Addressing

The script uses `0x10000 + (unique_index * 0x100)` to generate non-conflicting
unique space addresses for multiple overrides in the same function. This is a
safe approach with plenty of address space.

## Usage Recommendations

### For Production Use

Use `--type=stable` which includes only the anchor-based overrides:

```bash
# Scan for all stable suspects
python generate_pcode_overrides.py /path/to/pseudocode/src --type=stable

# Apply all stable fixes
python generate_pcode_overrides.py /path/to/pseudocode/src --type=stable --apply
```

### For Testing/Experimentation

Use specific experimental types with caution:

```bash
# Scan for experimental CALLIND preserve suspects
python generate_pcode_overrides.py /path/to/pseudocode/src --type=callind-preserve

# Scan all types (includes experimental)
python generate_pcode_overrides.py /path/to/pseudocode/src --type=all
```

## P-code Override Registration Flow

The registration flow during pseudocode export:

1. **Preload phase** (`exporter.py:158-213`):
   - Scans JSON files in `pseudocode/src/` for `pcode_overrides` key
   - Caches overrides in Python for preservation in output
   - Registers each override with `DecompileCallback.registerPcodeOverride(func_addr, instr_addr, pcode_list)`

2. **Decompilation phase**:
   - Ghidra's decompiler checks for registered overrides at each instruction
   - If found, uses the override P-code instead of lifting from the binary

3. **Cleanup phase** (`exporter.py:876`):
   - `DecompileCallback.clearPcodeOverrides()` frees memory after export
